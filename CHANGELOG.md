# Changelog

Dinnerbell follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and [Semantic Versioning](https://semver.org/). Before version 1.0, a minor release can change configuration or behavior; its **Upgrade notes** say what to do.

Every release lists **Upgrade notes**. Read them before you upgrade, and always back up first (see "Upgrade" in [docs/setup.md](docs/setup.md)).

## [Unreleased]

### Added

- **The optional assistant's core, behind a flag** (#17, [ADR 0009](docs/adr/0009-optional-assistant.md)). Nothing changes unless an operator sets `DINNERBELL_ANTHROPIC_API_KEY` and adds `assistant` to `DINNERBELL_FEATURES`; then Admin gains an **Assistant** tab. There the admin turns the assistant on, sets the household's **Monthly cap** ($1 to $100 a calendar month in the household's time zone, $5 by default) and **Conversation hours** (0 to 168, 24 by default), and sees this month's usage in total and per member. Each change is audited as `household.assistant_updated`. Members talk to it in Slack and on the web's **Assistant** page (below). This release adds what they build on:
  - Before each request to Anthropic, Dinnerbell reserves the most the request can cost and refuses it if that would pass the cap, then settles the reservation to what the request cost, cache tokens included. At the cap, the assistant says it's unavailable until next month.
  - Conversations are stored with members as "Member 1", "Member 2", and so on, and deleted once Conversation hours pass, every 5 minutes, or at once when the admin lowers the setting. No names, emails, Slack IDs, preferences, vetoes, ratings, or notes are sent.
  - The assistant's one tool so far looks up catalog items by name or tag, acting as the member with a member's permissions, even for an admin.
  - `DINNERBELL_ASSISTANT_MODEL` picks `claude-sonnet-5-5` (the default), `claude-opus-5-5`, or `claude-haiku-5-5`; Dinnerbell refuses to start on a model it has no prices for.
  - `dinnerbell scrub-test` turns the assistant off and deletes every conversation.
- **The assistant's candidates, drafts, and Confirm, still behind the flag** (#17). Four more tools, each acting as the member with a member's permissions, even for an admin:
  - **Find candidates**, for a call that's voting: what passes ranking's filters for everyone who's in, in name order, optionally narrowed by days since eaten, cuisine, or mode. Reasons come only from variety, novelty, suggestions, the usual mode, volunteer fit, and meal fit, with members as "Member 1" and so on; never hints, favorites, or what the filters removed. Before voting, the assistant says to ask once voting opens.
  - **Draft a proposal** of a candidate, **draft an offer** of a catalog item, and **draft catalog items** in the catalog file format. A catalog draft drops entries the catalog has already and lists them, and strips `cooks` and `active`.
  - Each draft says what **Confirm** does, such as join late, take the role the mode needs, or replace a scheduled call, lasts 30 minutes, and only its member can confirm it, once. Confirm runs the same service as the form, which checks everything again, so a stale draft gets the usual error and nothing changes. A catalog draft's Confirm opens the import preview, which only adds, even if a matching item appeared meanwhile.
  - The tools pick the call the member names, then the conversation's, then the only open one, and ask when several are open.
  - Expired drafts are deleted every 5 minutes, and `dinnerbell scrub-test` and `dinnerbell reset-history` delete them all. The web page and Slack have the Confirm and Cancel buttons (below).
- **The assistant on the web: the Assistant page, behind the same flag** (#17). With the key, the flag, and Admin's switch on, each active member and admin gets an **Assistant** link and a private conversation of their own; guests don't. A reply appears under the message without reloading the page, and the form works without JavaScript too. Reply text is plain text: no Markdown, and no clickable links. Each draft is a card that says what **Confirm** does, with **Confirm** and **Cancel**; a proposal or offer shows the service's result or its refusal on the card, and a catalog draft opens the import preview, which only adds. A draft that expired, was used, or isn't yours says so. **Start over** deletes the conversation and cancels its waiting drafts. At Conversation hours 0, the page says nothing is kept and shows only the latest exchange. Otherwise the link is hidden and the Assistant pages answer 404, as Admin > Assistant does.
- **Confirm the assistant's drafts in Slack** (#17). Each draft comes as a card after the reply, with what **Confirm** does, and **Confirm** and **Cancel**. In a channel thread the card shows only to the member who asked; in a direct message it's an ordinary message in the thread. **Confirm** runs the same service as the form, as that member, and the card then says what happened, or the service's reason it can't, such as a call that's no longer voting. A draft that's expired, used, or someone else's says so and changes nothing. A catalog draft's **Confirm** gives a **Review the import** link to the web's add-only import preview, signed for that member and good for 24 hours, as long as Dinnerbell keeps a confirmed catalog draft; nothing is saved until they select **Apply** there. While the assistant is off, the buttons say "The assistant is turned off." and change nothing. A word that only starts like `@here`, `@channel`, or `@everyone`, such as "@hereford", now reads as written in replies, and the note that Dinnerbell sees only mentions comes once to each member whose replies there were private, and once to the thread with its first public reply.
- **The assistant drafts catalog items from a menu link, behind the same flag** (#17). Give it a link to a restaurant's menu or a recipe, and it drafts catalog items for **Confirm**, which opens the import preview, as other catalog drafts do. Dinnerbell fetches the page under the same rules as every menu link (HTTPS, public addresses only, 2 MB, 10 seconds), and sends only its text, up to 60,000 bytes, to a separate drafting call with no tools, reserved and settled under the monthly cap like any other call. A message reads at most 2 links. The page is treated as data, never instructions: it sits between randomly named tags, the answer is only read as a catalog file, and the draft keeps at most 20 entries and drops every link and note the page gave. A draft of one place gets the member's own link, or the page's address when the link redirected within its own site. The assistant sees just how many items the draft adds and which ones the catalog has already.
- **Talk to the assistant in Slack, behind the same flag** (#17). With the key, the flag, and Admin's switch on, a member can message Dinnerbell directly, or mention @Dinnerbell in the household channel, and Dinnerbell answers in that message's thread. A direct message thread is private to its member. A channel thread is shared, each message acts as its author, and Dinnerbell's first reply there says it sees only messages that mention it. Dinnerbell answers active members only, and ignores bots, edits, and mentions outside the household channel: nothing from anyone else is stored or sent. Replies can't mention anyone or ping the channel, and hold no links: any address in one is written so Slack doesn't link it (`hxxps[:]//example[.]com`). Each member has one message answered at a time; another meanwhile gets a note that Dinnerbell is still on the last one. A direct message with a file gets "I can read only text messages." App Home shows a line saying members can message or mention Dinnerbell while the assistant answers them. Slack needs the new assistant variant of the app manifest, `deploy/slack-app-manifest.assistant.yaml` (`deploy/slack-app-manifest.assistant.test.yaml` for a test instance); the default manifests don't change.
- **The assistant answers within 100 seconds, and keeps who a Slack message mentions** (#17). A message that takes longer gets "I ran out of time on that one. Try asking for less at once." instead of running on after the web page stops waiting, and nothing of it is kept. In Slack, a mention of an active member reaches the assistant as that member's "Member 2", so "can <@Kim> cook?" keeps its meaning, and the reply names Kim; anyone else still goes as "@someone".
- **The assistant answers questions about meal history, behind the same flag** (#264). Ask "What's our most-ordered pizza place?" or "When did we last have Thai?" in any conversation, and the assistant looks it up in the meal log: each place or home meal the household ate, how often, and when last, narrowed by name, tag, kind, or dates. Each comes with its household hint, such as "Well liked", the same words every member sees on Catalog, under the same thresholds. It never says who ate, cooked, ordered, or rated, and sends nobody's own ratings or notes ([ADR 0009](docs/adr/0009-optional-assistant.md), amended).
- **The assistant shows that it's working in Slack** (#265). As soon as Dinnerbell takes a message to answer, the thread shows "Dinnerbell is thinking…" with a few rotating lines. Where Slack won't show that status, Dinnerbell reacts to the member's message with :hourglass_flowing_sand: instead. Either one goes when the reply posts, and after an error or the out-of-time line. The indicator never delays or blocks the reply, and messages Dinnerbell ignores show none. The assistant manifests add the `reactions:write` scope for the reaction.
- **The assistant drafts call actions, in any conversation, behind the same flag** (#251). In a DM, on the web, or in a channel thread, a member can ask the assistant to answer in, out, or maybe; join late; vote or take a vote back; suggest a catalog item; take or give up a role; take back an offer they made; invite a guest, saved or new with the dietary needs they name, and answer for a guest they invited; or start a call, or start a called-off one again. Each change is its own draft, so "I'm in, put me down for pickup, and vote for the noodle place" gives three cards, and each **Confirm** runs the same service as the button on the call, as the member with a member's permissions, even for an admin. A draft says what Confirm does, such as joining late first or withdrawing role offers on an Out, and the assistant refuses what the call wouldn't allow, such as answering after answers closed, taking back someone else's offer, or answering for someone else's guest. Guests are named only as the member wrote them. A new **Look up a call** tool gives the assistant the call's basics, the member's own answer, and the picks with whether the member votes for each; never anyone else's answer or vote. In a channel thread, the cards and their results show only to the member who asked.
- **The assistant drafts changes to a member's own preferences, feedback, and away days, in private only, behind the same flag** (#253). On the Assistant page or in a direct message with Dinnerbell, never in a channel thread, a member can ask "Veto mushrooms", "Rate last night's dinner: hated it, it was cold", or "I'm away Thursday through Saturday", and get a draft for each. **Confirm** runs what **Preferences** and the feedback form run, as the member with a member's permissions, even for an admin, and never Admin's path to someone else's preferences. A draft says what Confirm does, such as what feedback it replaces or that a veto keeps something out of every call they're in, and the assistant refuses what the form would, in the form's words, such as feedback after its 7 days or on a meal they didn't eat. If the member changes the same thing elsewhere first, Confirm says so and changes nothing. Two new lookups give the assistant the member's own levels and away days, and the meals they ate that still take feedback, with their own answers. Only these tools send a member's own preferences, ratings, feedback, or away days to Anthropic, only when that member asks, and never anyone else's: not who else ate a meal, who cooked it, or how anyone else rated it. Admin > Assistant says so. A cap too low for even one request, such as $1 with `claude-opus-5-5`, where one private message's worst case is now just over $1, gets a truthful reply that the cap is too low for the model, not that the month's limit is reached, and Admin > Assistant notes it with the least cap that covers the smallest message, saying long conversations need more.
- **The assistant's longer Slack replies appear as they're written** (#266). In a direct message, a reply of more than a couple of lines streams into its thread line by line, through the same defanging as any reply: no link, mention, or ping can get through however the text is cut. A streamed reply is standard Markdown, so bold, lists, and code show, and a `<` shows as `‹`. Short replies, every reply in a channel thread, and the web page don't change, and neither does what's stored. If Slack won't stream, the reply is posted as before, without repeating what the member already saw. The assistant is also asked to write no text before it calls a tool, so a tool round's preface doesn't show. No new scope or manifest change.
- **The assistant coordinates a call, in private only, behind the same flag** (#252). In a direct message with Dinnerbell or on the Assistant page, never in a channel thread, the coordinator can ask the assistant to lock a pick, break a tie, or shuffle the picks while voting; once it's decided, change the plan as **Adjust** does (the meal time, a catalog place, the way, and who cooks, orders, or picks up); hand off coordinating; mark the meal done once it's meal time; or call the call off, with a reason. "Lock the taco place, @Sam picks it up" gives one card that locks it and assigns the pickup together, so Sam hears once, and if the roles can't be assigned, nothing is locked. The member who started an ad-hoc call can call it off too, until it's decided. **Confirm** runs the same use case as the call page or Slack's button, as the member with a member's permissions, so the coordinator's own checks decide: an admin who isn't the coordinator is refused, as any member is, and uses the web instead. A change of plan that someone made elsewhere first is refused rather than written over. In a channel thread, the assistant says to ask in a direct message. People go to Anthropic only as "Member 2" and so on: a new lookup gives the coordinator's assistant who's in, with the roles they offered, how many guests are in, which picks are tied, and the plan; never anyone's vote, maybe, or out. The coordinator's cards and Confirm's results, which only they see, show names; the model reads only labels, and a refusal that would name someone, such as a cook list's, comes to it with the label. The seven new tools make each private message's worst-case reservation about 15% larger, about $0.31 with `claude-sonnet-5-5`.
- **The assistant edits the catalog and the meal log, in any conversation, behind the same flag** (#254). On the web, in a direct message, or in a channel thread, a member can ask the assistant to edit a catalog item, such as "Mark Siam Garden as delivery only", take one off the catalog or put it back, log a meal they had without a call, such as "We had Taqueria for lunch yesterday", or edit or delete a meal they logged. Each is a draft, and **Confirm** runs what the Catalog item form or History runs, as the member with a member's permissions, even for an admin: an admin's own History powers, such as changing someone else's meal, stay on the web, and renaming or merging tags is never a tool. A catalog edit's card is a before-and-after diff, one line for each field Confirm changes, with the new value first and in full, in Slack too, and nothing else changes. Cooks, and who ate, are named only by the conversation's labels, such as the member's own or a Slack mention's, and resolved to active members of the household when the draft is made, so the model can't make up a cook. If the item or the meal changed elsewhere after the draft, Confirm says so and changes nothing. A new **Look up my meals** tool gives the assistant the meals the member logged, with who ate as labels in private only: in a channel thread, whose reply posts for everyone, it leaves out who ate. An item's link, order link, and notes as they are go to nobody but the member's card. In a channel thread, the cards and their results show only to the member who asked. The three new tools, and the prompt's lines about them, make each message's worst-case reservation about 6% larger in private and 7% in a channel thread: about $0.33 for a private message with `claude-sonnet-5-5` (from $0.31), and $1.23 with `claude-opus-5-5` (from $1.16). A channel thread's message with `claude-opus-5-5` now reserves about $1.03, so a $1 cap with that model answers no message at all, and Admin > Assistant now says so.

### Changed

- **Shuffle proposals is easier to find on the web** (#267). On Today and the call page, the button now sits under the proposal list, where Slack puts it, with its "N left" note, and has a border so it reads as a button, while **Vote** still stands out. Who sees it is unchanged: the coordinator and admins, while a shuffle is left.

### Fixed

- CI only: when the runner can't install podman-compose with apt, the `compose` job installs the same version, 1.0.6, from PyPI with the dependency versions Ubuntu 24.04 ships (#281). On 2026-11-11 the runners' DNS failed for every `ubuntu.com` host for hours, and `publish`, which waits for `compose`, couldn't run. Each apt run is capped at 2 minutes, and the job's limit is 15 minutes.

### Upgrade notes

- **Migration 0031** adds two empty tables, `assistant_usage` and `assistant_conversation`. It changes no existing row, and nothing reads the tables unless the assistant is configured. A downgrade to 0.15.0 drops them, with any usage and conversations in them.
- **Migration 0032** adds one empty table, `assistant_draft`, for the assistant's drafts. It changes no existing row, and nothing writes the table unless the assistant is on. A downgrade to 0031 drops it, with any drafts still waiting for Confirm.
- **Migration 0033** adds `assistant_draft.confirmed_at`, empty for every draft saved before it. A catalog draft confirmed in Slack before the upgrade loses its **Review the import** link; ask the assistant again. A downgrade to 0032 drops the column.
- **Migration 0034** rebuilds `assistant_draft` so its `kind` accepts the call actions (#251), keeping every draft and its IDs. A downgrade to 0033 deletes call-action drafts still waiting for Confirm.
- **Migration 0035** rebuilds `assistant_draft` again so its `kind` accepts drafts of a member's own data (#253), keeping every draft and its IDs. A downgrade to 0034 deletes those drafts still waiting for Confirm.
- **Migration 0036** rebuilds `assistant_draft` again so its `kind` accepts coordinating drafts (#252): `decide`, `shuffle`, `plan`, `hand_off`, `mark_done`, and `call_off`. It keeps every draft, its IDs, and the AUTOINCREMENT high-water mark, so an old Confirm button never reaches a newer draft. A downgrade to 0035 deletes those drafts still waiting for Confirm.
- **Migration 0037** rebuilds `assistant_draft` again so its `kind` accepts catalog edits and the meal log (#254): `item_edit`, `item_active`, `meal_log`, `meal_edit`, and `meal_delete`. It keeps every draft, its IDs, and the AUTOINCREMENT high-water mark, so an old Confirm button never reaches a newer draft. A downgrade to 0036 deletes those drafts still waiting for Confirm.
- **New dependency:** the image now includes Anthropic's `anthropic` SDK and its dependencies (Apache-2.0, MIT, and BSD). Dinnerbell sends nothing to Anthropic unless you set the key and the flag.
- **The cap is per database:** production and a test instance each keep their own. If you turn the assistant on, also set a monthly spend limit on the key's workspace in the Anthropic Console as a backstop, and give the test instance its own key.
- **Slack manifest, only if you turn the assistant on:** before you turn on Admin's switch, paste `deploy/slack-app-manifest.assistant.yaml` under **App Manifest**, set your hostname again, and reinstall the app (on test, `deploy/slack-app-manifest.assistant.test.yaml`). It adds a writable Messages tab, the `im:history`, `app_mentions:read`, and `reactions:write` scopes, and the `message.im` and `app_mention` events. If you applied an assistant manifest from an earlier build, such as on a test instance, paste it again and reinstall, so the app gets `reactions:write`; until then, a message gets only the status, where Slack shows one. Without the assistant, keep the default manifest. See "The assistant" in [docs/configuration.md](docs/configuration.md#talk-to-it-in-slack).
- **Keeping the key in a file:** `compose.secrets.yaml` doesn't mount `DINNERBELL_ANTHROPIC_API_KEY`, so installs that keep secrets in files need no new file. To keep the key in one, see "The assistant" in [docs/configuration.md](docs/configuration.md#the-assistant).

## [0.15.0] - 2026-11-09

### Security

- **pydantic 2.14.2** fixes two medium-severity validation bypasses (GHSA-qpmf-fgh3-ff25 and GHSA-3r8g-cqwr-jr29). Both need a model, `TypedDict`, or dataclass that allows extra fields, which Dinnerbell never uses, so neither could be reached. Routine updates come with it: pydantic-settings 2.16.2 and python-multipart 0.0.33 in the image, uv 0.13.7 for the build, and newer development tools.

### Added

- **Dinnerbone's Den on a call's page** (#241). With fun mode on, a call's own page, the one **View on web** in Slack opens, now has the den at the top, beside **Today**, as Today has it beside the greeting. There it follows that call rather than Today's next open call: laps while it takes answers, the wheel while it's voting, eating once it's decided. Locking or marking done the call on its page celebrates as it does on Today, and its card's refresh keeps the den current. Badges still flip on Today only. With fun mode off, the page is as before.

### Changed

- **A guest shows once on a call's page** (#238). A guest who was in used to be listed twice: in **Who's in**, and again under **Guests** with "invited by". Now **Who's in** lists each guest once, marked "Guest invited by Sam", and the **Guests** list is gone. Everything you could do there is on the guest's row: their dietary needs, **In** and **Out** and the roles for a guest you answer for, and **Take off the call**. A guest who's out stays on the list as out, and one taken off the call or removed keeps their answer's row, marked "Guest". A guest with Slack who hasn't answered yet has a row marked **No answer yet** while answers are open, and leaves the list when answers close, as a member who never answered does. **Invite a guest** is where it was. The Slack call message already listed each guest once, and App Home has no roster, so they don't change.
- **Details no longer asks how many guests you're bringing** (#240). On a call, guests come only from **Invite a guest**, which names each one and their dietary needs, so **Details** on the web and in Slack drops **Guests** and **Guests' dietary needs**, and keeps your eat window, a suggestion, and a note. A guest count already saved on a call keeps counting: in the head count, ranking, the decision, history, stats, and hosting badges. Offers keep their guest count, since an offer has no invitations.
- **Every "nothing" choice in a menu is in square brackets, with the same words on the web and in Slack** (#239). A choice that means nothing names it, and a menu that needs a pick asks for one:
  - **Suggest from the catalog**, and **From the catalog** in **Add a proposal** and **Make an offer**, now offer **[Nothing from the catalog]** on the web, as in Slack, instead of **[Nothing]** and "Something new instead". **A saved guest** offers **[No saved guest]**, instead of "Someone new instead".
  - **Hand off coordinating** on a call's page starts on **[Choose someone]**, so you can't hand off to the first name by accident. It lists only members who can take it: once a call is decided, only those who are in, and never someone switched off. Before, it listed members a hand-off then refused. With nobody to list, the form is gone instead of showing an empty menu.
  - On the web, **Cuisine** reads **[Choose a cuisine]**, and **Log a meal** reads **[Choose from the catalog]**. **Change the plan** reads **[Keep *the place*]**, **[No cuisine]**, and **[Whichever the place allows]**. The catalog filters read **[All kinds]**, **[Any way]**, **[Any meal]**, **[Any tag]**, and **[All]**, and **Merge into** reads **[Choose a tag]**.
  - In Slack, a menu with nothing picked shows a bracketed placeholder instead of Slack's own "Select an item": the same words as its "nothing" choice, such as **[Nothing from the catalog]**, or **[Choose someone]**, **[Choose a way]**, **[Choose a meal]**, **[Choose a cuisine]**, **[Choose from the catalog]**, or **[Choose who ate]** where it needs a pick. **Who picks up** in **Assign roles**, and a role nobody holds in **Adjust**, read **[First who offered]**, which is who gets it when you leave it empty. A role in **Adjust** held by someone the menu can't list, such as a member made inactive, reads **[Choose someone]**, and leaving it empty keeps them. **Adjust** shows **[Keep *the place*]** on its place menu, **[Whichever the place allows]**, and **[No cuisine]**, and **Invite a guest** shows **[No dietary needs]**. **Either way** in the ⋯ beside a pick is now **[Either way]**.

  The messages these menus show when you leave them empty say **Choose** to match: "Choose someone.", "Choose another active member.", "Choose who does it.", "Choose who coordinates.", "Choose how to get it.", and "Choose a cuisine for it". Nothing a form sends changes.

### Fixed

- **Dinnerbone keeps running while you scroll** (#242). During a lap around the call card, scrolling paused him until it ended, and on a phone, the toolbar sliding away mid-scroll sent him back to the den to start over. Now he runs through a scroll, and when the window changes size, the phone turns, or the card grows or moves, he carries on around the card's new outline at his usual pace instead of starting over.

### Upgrade notes

- **Guest counts on open calls (#240):** nothing in the database changes. A call open at the upgrade keeps any guest count already saved on it, and it counts until the call ends; saving **Details** leaves it as it is, and nobody can change it there anymore, so to bring someone else, invite them as a guest. A **Details** page or Slack modal opened before the upgrade still saves: its guest count and guests' dietary needs are ignored, whatever they say.

## [0.14.0] - 2026-11-08

### Security

- **The base image moves to the current Python 3.12 slim digest**, which has the fixed `apt` for CVE-2026-109518. Grype flagged the old `apt` in 0.13.0's image at high severity. Dinnerbell never runs `apt` once the image is built, so the flaw couldn't be reached in a running container, but the scan blocks CI until the image has the fix.
- **The image installs Debian's fixed zlib** (CVE-2026-85091 and CVE-2026-76844, both high). No `python:3.12-slim` digest has it yet, so the image installs `zlib1g` 1:1.3.dfsg+really1.3.1-1+deb13u1 from Debian security until one does. Dinnerbell doesn't compress anything itself; Python and its libraries load zlib for compressed data, such as gzip.

### Added

- **Choose light, dark, or auto** (#231, FR-64). On **Preferences**, and on a guest's dietary-needs page, the new **Light or dark** card beside **Fun mode** sets how your pages look: **Auto**, the default, matches your device as before, and **Light** or **Dark** stays that way on every device you sign in on. Your phone's address bar follows too. An admin can change a member's from **Admin** > **Members**, audited as `member.color_mode_set`. The sign-in page always matches the device.
- **Change the place after a decision** (#219). When you end up eating somewhere else, the coordinator or an admin can record it until the meal is marked done: **Adjust** in Slack (the coordinator), or **Change the plan** on the web, which is the new name for **Change the time or who does what**. Choose any active catalog place or type a new name, with a way the place allows. Vetoes, dietary needs, the variety window, and who offered don't block it, because it records what happened. People keep their roles if the new way still has them. The decision updates in place, each person who's in gets one message before the meal time, and after it only someone you hand off to in the same save is messaged. History, ratings, and **How was it?** name the new place. It's audited as `event.place_changed`. Correcting the place after **Mark done** is a separate change (#220).
- **Correct the place after a meal is done** (#220). When a meal was marked done before the household changed its mind, an admin can correct the place under **Change the plan** on the call's page: any catalog place or a new name, with a way the place allows. History, stats, ranking, and the variety window use the corrected place, and feedback on the meal moves to it. Answers that don't fit the new kind stop showing and counting until a correction brings the kind back. The meal's counts and badges follow, as when an admin corrects who did what, and it's audited as `event.place_changed` with `after_done`, and `event.contributions_recounted` when a count moved. Nobody gets a message, and the posted messages update.
- **Put a takeout proposal back to "either way"** (#212). While voting, the coordinator or an admin can now put a proposal whose way they chose, **Pickup** or **Delivery**, back to not chosen: tap the chosen way again on the call page, or pick **Either way** in the ⋯ beside it on the proposals message. If someone else changed the way since your page or message showed it, Dinnerbell refuses the tap, says what the way is now, and changes nothing. The proposal keeps the way it shows, without "(chosen)", and if it wins, the decision asks the coordinator to choose, as for a proposal nobody set. The same people can do it as can choose the way. Audited as `event.way_set` with `mode: null`.

### Changed

- **The web pages have a new look: Hearth** (#230). The warm clay colors are cleaned up, and every page uses the Figtree font, which Dinnerbell serves itself, so no page loads anything from another site. Every chosen control now looks the same: In, Maybe, or Out, a tag, a meal, a role you offered, and a takeout way are all filled with the accent color and its text. **Vote** is the exception: it stays the solid orange button until you vote, then turns into a light tint marked **✓ Voted**, so it doesn't look like something left to tap. The page you're on in the menu and the tabs keeps its light tint, since it's where you are, not a choice. Preference levels keep their colors, and a chosen level now shows all four edges. Corners use one scale, and dark mode is ready to be chosen per member, not only taken from the device. Inactive members and items, and people who are out, now read in the muted text color instead of fading, so they stay readable.

Try again." after a server error, and "Not saved. Reload the page." when your session has expired. A request with no answer after 15 seconds gives up and says it might not have saved. Before, every failure said "Not saved. Reload the page.", and a stalled request left the button waiting with no end. A preference row that didn't save goes back to the level it last saved, and the banner stays until each card or row that failed saves, or that card refreshes.
- **An error on a call card scrolls into view** (#153). When a call refuses a tap, such as one that lost a race, its error at the top of the card now scrolls into view instead of staying above the screen on a tall card. With reduced motion, it jumps there without scrolling smoothly.
- **A tap shows at once** (#153). Buttons, preference levels, and chips now darken or lighten the moment you press them, instead of showing nothing until the save comes back, and their text keeps its contrast in both themes. A pressed chip that links shows its border. With motion allowed, a pressed control also shrinks slightly, and colors ease over about a tenth of a second, so a choice you change on a call card, such as **In** or **I can cook**, eases into place. A card's refresh that changes nothing moves nothing. With reduced motion, every change is instant.
- **A slow save shows that it's working** (#153). When an answer, vote, or preference takes longer than 150 milliseconds, the control you tapped dims and the pointer shows progress until it saves. A save that's faster than that shows nothing, so a quick tap doesn't flicker, and a card's refresh never dims it. Screen readers hear the card or row as busy until the new one arrives.
- **A full-page form posts once** (#153). Forms that load a new page, such as **How was it?** and **Fun mode**, dim their buttons while they post, and a second tap or click is ignored, so a double tap no longer posts twice. If you go back to the page, or the next page doesn't load within 10 seconds, such as when you stop it, the form works again. A form that isn't sent, because a field is missing or a catalog file is too big, isn't affected, and neither is one you send with Ctrl, Cmd, or Shift held, which can open the result in another tab or window.
- **"Saved" fades on Preferences** (#153). The "Saved" beside a preference you change now fades after about 2 seconds, instead of staying on every row you changed. With reduced motion, it disappears without fading. Screen readers can still read it.

### Removed

- **The upgrade guard for old feedback forms** (#148). 0.11.0 refused a **How was it?** form or modal opened before the upgrade, which still asked about the food and the place, so that saving it couldn't take back your rating. Both instances now run 0.11.0, so the guard is gone. A rating is now simply required: the web form and the Slack modal always send one, because a rating, **No answer** at first, is always selected. A web post without one gets the **Request refused** page, a Slack modal without the rating closes, and one with no rating picked says "Pick a rating, or No answer." None of them saves anything.

### Fixed

- **The last tap is the one that sticks** (#153). On a call card, tapping **Maybe** and then **Out** before the first answer came back saved **Out** but showed **Maybe**. On **Preferences**, tapping **+1** and then **+2** in the same row saved and showed **+1**. Now a tap on another choice replaces one still on its way, so the card or row shows and saves your last choice, and the replaced tap raises no error. Now each card refreshes on its own, a tap replaces a refresh in flight, and a refresh never starts while a tap is saving. A card skips its refresh only while you type in one of its fields or have one of its forms open, not just because a button in it has focus, and a refresh no longer dims the card's buttons.

The backend never reaches the final image.

- The Slack manifests no longer request the unused `channels:history` scope, so a stolen bot token can't read channel history.
- `compose.yaml` (and so the test instance) now sets `pids_limit: 256`, `mem_limit: 512m`, and rotated `json-file` logs (10 MB, 3 files), and `scripts/check-compose.sh` checks them. See "Resource and log limits" in docs/setup.md for what each podman-compose version honors.
- A test now compares the vendored htmx file with the SHA-256 of the npm `htmx.org@2.0.11` release, so a modified file fails CI. `CONTRIBUTING.md` says how to update it.
- The promotion checklist and "Verify an image" now verify the attestation against the pulled image's digest, and docs/setup.md and docs/hardening.md say to pin production to that digest or the version tag, and that the test instance's `main` tag moves.
- The four secrets (`DINNERBELL_SECRET_KEY`, `DINNERBELL_OIDC_CLIENT_SECRET`, `DINNERBELL_SLACK_BOT_TOKEN`, and `DINNERBELL_SLACK_APP_TOKEN`) are now files in `secrets/` (test: `secrets-test/`) that compose mounts at `/run/secrets`, and no longer lines in `.env`. podman-compose passed every `.env` line to podman as `-e NAME=value`, so while podman created the container, each secret was on its command line, visible to other local users in `ps` and printed by `podman-compose --dry-run` and `--verbose` (#35). Dinnerbell, `deploy/dinnerbell-test`, its shared-secret check, and `dinnerbell config check` (new option `--secrets-dir`) all read the files. A missing, unreadable, directory, multi-line, or oversized (over 8 KiB) secret file, or a broken symlink, stops startup with a message that names the file. The new `deploy/check-secrets` checks the four files before `up` and prints no value. `secrets/` and `secrets-test/` are git-ignored, left out of the image build context, and `scripts/check-compose.sh` (run in CI) fails when git tracks anything there except the `*.example` placeholders.

Calls already counted keep their counts.

### Fixed

- A Slack or internet outage no longer drops queued notifications (#14). An unavailable channel used to burn all 8 attempts in about an hour, and every pending row failed for good. Now an outage doesn't count as an attempt: rows retry at least every 5 minutes and are delivered, in order, when Slack returns. A response reminder queued before the call went to a vote, was decided, or finished is also dropped unsent instead of arriving late. The 24-hour limit counts from the newest update merged into a row. It is final: after 24 hours a call-opened, proposals, decision, badge, or recap post is lost for good (badges are marked announced and the recap marker moves when the post is queued), and you see `notification expired` in the log and `outbox.failed` in `/healthz`. `/healthz` now also reports `outbox.oldest_pending_age` (seconds) and shows `degraded` when the oldest waiting notification is over an hour old. Dinnerbell ignores a button press whose Slack `trigger_id` it handled in the last 10 minutes (it remembers up to 2,048), which is how Slack repeats a press after a reconnect. The example file now holds `REPLACE-ME-with-48-random-characters`, and `deploy/check-secrets` flags a placeholder, short, or repetitive key before you start.

If the first holds the lock for about 15 seconds, `migrate` and `serve` print a clear message and exit with status 1.

- Docs (#99): the ranking page, the spec, and ADR 0007 no longer say a place in the vote is always drawn. The last place is only not reserved for a suggestion, so at temperature 0 it can be one. The 0.7.0 entry below still has the old wording.

The removal takes effect only after the reinstall, and nothing breaks before it.
- **A `DINNERBELL_SECRET_KEY` with a placeholder marker makes the service refuse to start, and under `restart: unless-stopped` it crash-loops.** Run `deploy/check-secrets` before `up`. The refused keys are the text in `secrets/DINNERBELL_SECRET_KEY.example`, any key containing `example`, `replace`, `changeme`, `placeholder`, `yoursecret`, or `secretkeyhere` (case, `-`, and `_` ignored), and any key with fewer than 8 distinct characters. Keep your old key if it is long and random: marker words and fewer than 8 distinct characters are the only new triggers. If you do rotate the key, that invalidates only open login pages and import previews, not sessions (sessions are random server-side tokens).
- **Hard stop: create four secret files before you run `up` on this release.** The new `compose.yaml` mounts `secrets/DINNERBELL_SECRET_KEY`, `secrets/DINNERBELL_OIDC_CLIENT_SECRET`, `secrets/DINNERBELL_SLACK_BOT_TOKEN`, and `secrets/DINNERBELL_SLACK_APP_TOKEN`. If you pull and run `up` first, the service won't start. What happens with a missing file depends on the tool: podman-compose 1.0.6 and 1.6.0 pass the path to podman as a `--volume` without checking it (confirmed in their source), and podman refuses a bind mount whose source is missing (documented, not run here). Docker creates a directory for a missing `-v` source; what Docker Compose does for a missing secret file is not verified. A directory in place of a file makes Dinnerbell stop with an "is a directory" message. Run `deploy/check-secrets` (new) first: it reports a missing file, a directory, a mode other than 600, and an empty file (except an empty Slack token file, which turns Slack off), and prints no value. Dinnerbell itself still accepts a secret from `.env` for this one release, with a warning for each; the next release ignores `.env` for these four. If a value is in both `.env` and its file with different values, Dinnerbell refuses to start. Run this from the clone, with the service still running:

  ```sh
  ( umask 077
    mkdir -p secrets
    for name in SECRET_KEY OIDC_CLIENT_SECRET SLACK_BOT_TOKEN SLACK_APP_TOKEN; do
        sed -n "s/^[[:space:]]*\(export[[:space:]]\{1,\}\)\{0,1\}DINNERBELL_$name[[:space:]]*=[[:space:]]*//p" .env | tail -n 1 | tr -d '\r' | sed -e 's/[[:space:]]*$//' -e 's/^"\(.*\)"$/\1/' -e "s/^'\(.*\)'\$/\1/" | tr -d '\n' >"secrets/DINNERBELL_$name"
    done )
  deploy/check-secrets --env-file .env      # every secret must say "match"
  for name in SECRET_KEY OIDC_CLIENT_SECRET SLACK_BOT_TOKEN SLACK_APP_TOKEN; do
      chmod 600 "secrets/DINNERBELL_$name"
      podman unshare chown 10001:10001 "secrets/DINNERBELL_$name"
  done
  ```

  The `sed` reads each value from `.env` without putting it on a command line, removes one pair of enclosing quotes and nothing else, and leaves no trailing newline. `deploy/check-secrets --env-file .env` compares SHA-256 hashes and prints only `match` or `differs`; run it before the `chown`, because afterward your account can't read the files. If a value has a trailing `# comment` or an escape in double quotes, write that file by hand: `printf '%s' 'the value' >secrets/DINNERBELL_SECRET_KEY` (put a space before the command to keep it out of your shell history), then `chmod 600` and `chown` it. An empty file is fine for a Slack token you don't use, but the file must exist. Then delete the four lines from `.env`, pull the new image, and run `podman-compose down && podman-compose up -d`. Check that the log has no "is set in the environment" warning.
- With rootful Docker, replace `podman unshare chown 10001:10001` with `sudo chown 10001:10001`. The files must belong to UID 10001, the user inside the container, with mode 600: compose bind-mounts them as they are and ignores `uid`, `gid`, and `mode` for file secrets, so a file owned by your own account is unreadable inside the container. Your own account can no longer read the files afterward; to replace one, delete it, write it again, and `chown` it again.
- If Dinnerbell stops at start with `Can't read the secret file`, the owner or mode is wrong: run the `chmod` and `chown` again. If it says the path `is a directory`, the file didn't exist when the engine mounted it: remove the directory, create the file, and recreate the service. The table in "Keep secrets in files" in [docs/setup.md](docs/setup.md#keep-secrets-in-files) lists each message.
- **Test instance:** do the same for `.env.test`, into `secrets-test/` instead of `secrets/` (the `sed` reads `.env.test`). The new `deploy/dinnerbell-test` refuses to start without the four files in `secrets-test/`, and, as before, refuses a secret that test shares with production, now in files as well as in `.env` and `.env.test`. It compares SHA-256 hashes, and reads files owned by UID 10001 through `podman unshare` (with Docker, run it with `sudo`).
- Food Critic upgrade: no migration, settings, or Slack scope changes. Food Critic awards made before the upgrade stay out of the recap and the newest badges; ones earned after it appear in both. No Food Critic tier is ever announced.
- The next prewarm uploads 5 more files, one per Food Critic tier, two seconds apart.
- **Resource and log limits.** `compose.yaml` now sets `pids_limit: 256`, `mem_limit: 512m`, and `json-file` log rotation (10 MB, 3 files). They apply when you recreate the service with `podman-compose down && podman-compose up -d`. If the service is close to 512 MB on your host, check `podman stats` first.
- **`/healthz` changes.** It gains `backup.failing` and `outbox.oldest_pending_age` (seconds), and reports `degraded` when the newest nightly backup failed or the oldest pending notification is over 1 hour old. A monitor that alerts on anything other than `ok` can fire where it didn't before.

Someone assigned who hadn't offered is told the coordinator assigned them. Nobody is told about a role until it's settled. With no coordinator, the role is assigned at once as before, and an admin can still use **Assign roles**.
  - **Break the tie.** When picks are tied for the most votes, the coordinator sees **Break the tie** beside each tied pick, on the picks message and the event page, and chooses one even if they didn't vote. It decides at once. If nobody chooses, the deadline breaks the tie in this order: the coordinator's counted vote on a tied pick, then an admin's vote (only with no coordinator, or a guest coordinating), then the tied pick eaten longest ago (never eaten counts as longest), then the order the picks were drawn in. The decision says how: "Tied; Kim (coordinator) chose", "Tied; least recently eaten", or "Tied; drawn at random". A late joiner's vote that doesn't count never breaks or makes a tie.

The new picks pass every rule the first draw does (vetoes, guests' needs, someone to do it, the variety window, one pick per place, the meal) and leave out the places just shuffled out unless nothing else fits. The picks message updates in place with "Kim shuffled the picks (2 replaced)." and mentions no one, a short note goes in the call's thread, and the web shows the new set on refresh. Each shuffle is audited and logged with its counts.

All of them can be changed there, like lunch's and dinner's.

- Join a call late, during the vote (#76). If you missed the answers, by saying out, being a maybe when answers closed, or not answering, you can still join while the call is voting: tap **I'm in (late)** on the call message, your Your answer card, App Home, or the event page. Voting or adding a pick while you're not in asks "You missed the answers. Join late?" first, and joins you if you say yes. Guests are unchanged: they come by invitation, while answers are open.
  - You're in, and the call message, the picks, and the decision say you joined late. You count in the head count, you can offer to cook, pick up, or order (on your card, Home, or the web), and you can be assigned a role.

They're on the event page and in the ⋯ beside each late joiner on the picks message. Each change is audited and updates the call's messages.
  - Your dietary needs and vetoes don't remove picks already made. Only you see which picks don't fit your preferences, on your Your answer card, App Home, and the event page; nobody else, the coordinator included, sees anything that could say what you veto. Guests you bring count as any guest does: picks added from then on must meet their dietary needs, and a pick already made that misses them stays and warns everyone, on the decision too. Your own needs stay off the decision's "Dietary needs" line, which would give them away. Joining late clears guests and an eat window left on an earlier answer. ### Changed

- Proposals are drawn at random, weighted by score, instead of the top scores with ties broken by name (#78). With a fresh catalog most places score the same, so every call used to propose the same three places, first in alphabetical order. See [How Dinnerbell picks proposals](docs/ranking.md), with a worked example.
  - Vetoes, guest needs, coverage, the variety window, meal fit, and one pick per place still apply first, and absolutely. The draw only chooses among places that pass all of them, and the vote still gets its usual number of picks.
  - Places with the same score have the same chance, whatever their names. A place 1 point better is about 2.7 times as likely to be picked, so the best place usually makes the vote but not every time.
  - A place someone suggested for the call is always proposed when it fits, ahead of the draw.
  - After each pick, places sharing its cuisine become less likely, so a vote rarely has three of one cuisine when others fit.
  - The same call always draws the same picks. A re-run, or starting a called-off call again, draws again. The order drawn is the proposals' rank, which still breaks a tied vote when neither the coordinator nor an admin voted for a tied place.
  - **Admin > Ranking** has a new **Randomness** setting, from 0 to 3, default 1. Lower sticks closer to the best scores, and 0 always picks them in order, with ties drawn at random. Higher mixes the picks up more. Changing it is audited with the other ranking settings.

Each Slack tap and scheduler run has a `request_id`, as web requests do, so one tap's lines group together. A change applies from the next call: a call that's already out, or scheduled for a later day, keeps its times, and a call started again uses the new ones. If today's call hasn't gone out yet, it follows the new schedule when it still can; moving the call to a time that has already passed today keeps today's call at the old time, and the post says so. Saving without a change posts nothing, and a save over someone else's newer change is refused so it can't undo theirs.
- `/dinnerbell schedule` shows each meal's call time, when answers and voting close, and the usual meal time, with a **Change the schedule** button that opens the Schedule page. It no longer says "coming soon".
- Ask about a later day's meal now (#59). A call you start for a later day still posts at that day's usual time, and now you can post it early instead: select **Post it now** on the reply in Slack, on App Home, or on the call's web card, add `now` (or `early`) to the command, as in `/dinnerbell call lunch tomorrow now`, or check **Post it now** on the web's start form. Responses open at once; the response deadline, the reminder, and voting stay at that day's usual times. The call message names the day ("Who's in for lunch on Sunday, Oct 25? Answer by 11:30 AM that day."). Any member who could start the call can post it, a call that's posted already is left as it is, and posting is recorded in the audit log. Re-running a call posted early, or calling it off and starting it again, posts the new run at once.
- App Home and Today list calls scheduled for later under **Coming up** ("Lunch · Sunday, Oct 25 · posts at 10:30 AM"), with **Post it now**, and **Call it off** for whoever may call it off.
- Feedback after meals (#12, FR-45 to FR-49). Everyone who ate a meal can say how it was, for 7 days after it, and change their answer until then. Each part is optional: the food (loved it, fine, or not again); the place, for a restaurant, with issues such as late or cold; and, for a home meal, a thank-you to the cook with an optional note of up to 200 characters. Feedback doesn't change proposals yet.
  - In Slack, a done call's decision message has **How was it?**, and App Home lists meals from the last week you haven't rated yet.
  - On the web, History and a done call's page have **How was it?**, and show your own answers.
  - The catalog shows how many loved each item's food and place. "Fine," "not again," and place issues are kept for later but never shown, not even as counts. Cooks see who thanked them and their notes; everyone else sees only how many thank-yous there were. Nobody, admins included, sees who chose "not again", on any page, in Slack, or in the catalog file.
  - Turn on the feedback reminder in Preferences to get one direct message after each meal you ate. It's off by default, and muting direct-message reminders stops it too.
  - Changing a meal's item in History deletes its feedback, and taking someone off a meal deletes theirs, because it was about a meal they no longer ate.
  - On a test instance, discarding a call deletes the feedback on its meal, and `scrub-test` deletes all feedback; both show how many rows, as a number only.
- Slack says which version is answering. `/dinnerbell version` (`/dinnerbell-test version` on test) replies privately with the version as the web footer shows it, such as `0.3.0`, or `0.3.0+abc1234` for a build from `main`; the instance label, if one is set; the database's schema revision; and a link to the release notes, or to the commit for a `main` build. The help reply lists `version` and ends with a version line, such as "Dinnerbell 0.3.0+abc1234 · TEST", and so does the bottom of App Home.
- On a test instance only (`DINNERBELL_INSTANCE_LABEL` set), an admin can discard a call so a fresh one can start for the same slot and day (#60): **Discard (test)** on the call's card, behind a confirmation page; `/dinnerbell-test discard [lunch|dinner] [day]`; or `dinnerbell discard-call ID [--yes]`, which shows what it will delete first. Discarding deletes the call with its answers, suggestions, proposals, votes, decision, assignments, logged meal, and unsent notifications, edits its Slack messages to "Discarded (test)", and writes an audit row. On test, a called-off call can also start again at any time, not only until the usual meal time plus two hours. On production none of this appears: the pages are a 404, the slash command and the CLI refuse, and the rules don't change. See [docs/setup.md](docs/setup.md#discard-a-call-and-start-again).

### Changed

- Admin > Schedule is now **Admin > Ranking**. It keeps the ranking weights, proposals per call, variety window, and **Skip a day**; call times and windows moved to the Schedule page.
- A schedule that's on must close voting before the usual meal time; you can always turn a slot off. Saving one that doesn't, such as a 3:00 PM call with 90 minutes to answer and 45 to vote and a 5:00 PM meal, explains how to fix it. Schedules already saved keep working.
- Call IDs are never reused. Before, a new call could take the ID of a call deleted before it. The upgrade rebuilds the `event` table (migration 0007) and keeps every row.
- In Slack, you can now see what you chose on a call (#42, #52). While responses are open, the call message has one **Answer** button instead of **In**, **Maybe**, **Out**, the role offers, **I'll coordinate**, and **Details**. **Answer** posts a Your answer card only you see, with those buttons and your answer and offers selected: green, and marked "✓ " so you can tell without color. Taps on the card change the card in place instead of adding another message. Tapping **Answer** again adds a new card, because Slack can't change one person's view of a shared message. The card replaces the "Thanks! You're offering to cook" lines, which piled up. While voting with nobody coordinating, the call message still has **I'll coordinate**.
- The reminder direct message and App Home show your answer selected the same way. A tap on the reminder changes the reminder itself, instead of adding a confirmation under it.
- A card or reminder left over from before a call moved on (responses closed, called off, or started again) says "This call moved on." instead of answering the newer call.

### Fixed

- Starting a call for a later day in Slack no longer says "Started … It's posted in the Dinnerbell channel." when nothing is posted until that day (#59). The reply says "Scheduled the lunch call for Sunday, Oct 25. It posts in #dinnerbell at 10:30 AM that day." A scheduled call's web card says when it posts, and which day, instead of "Opens at 10:30 AM."
- A call scheduled for a later day no longer hides **Start a dinner call** (or lunch) for today on App Home.
- **I'll coordinate** on a voting call message names the call's run, so a message from before a call-off and restart can't make you coordinator of the new run (#54).
- **Start the vote now** and **Decide now** no longer show once the window's deadline has passed. Until the scheduler's next tick moved the call on, up to 30 seconds later, the web card and App Home still offered them, and selecting one only said the call had moved on.
- In Slack, picking **Start the vote now** or **Decide now** from the call's ⋯ menu after the deadline says the call has moved on right away, instead of opening a confirmation that could only fail.
- Tapping **I'll coordinate** again when you already coordinate no longer says someone else is coordinating.
- Details saved in Slack after the call was called off and started again no longer change the new call.

### Upgrade notes

- The audit log names schedule changes differently. Ranking changes on Admin > Ranking are now `household.ranking_updated`, and a member's change to a slot's schedule is `household.slot_schedule_updated`. Rows written before you upgrade keep `household.schedule_updated`. If you search the audit log for schedule changes, search for all three.
- The database migrates to revision `0008_meal_feedback` when Dinnerbell starts, in two steps: `0007_event_autoincrement` rebuilds the `event` table so call IDs are never reused, keeping every row, and `0008_meal_feedback` adds an empty `feedback` table. Both are quick for a household's data. Back up first, as always. To go back to an earlier release, restore that backup: older releases refuse a database at a revision they don't know.
- Decision messages for calls that finished before you upgrade don't get **How was it?** until they're redrawn. Those meals still take feedback from App Home and the web.
- Members who already turned on the feedback reminder in Preferences, which did nothing until now, start getting it for meals that finish after the upgrade, unless they muted direct-message reminders.
- Optional: the Slack app manifests list `version` in the slash command's usage hint. To show it in Slack, open the app's **Slash Commands** settings and edit the command's usage hint to match `deploy/slack-app-manifest.yaml` (or `deploy/slack-app-manifest.test.yaml` for test). `/dinnerbell version` works without this.
- Optional, for test: the test Slack app's manifest lists `discard` in the slash command's usage hint. To show it, edit the `/dinnerbell-test` command's usage hint to match `deploy/slack-app-manifest.test.yaml`.
- Call messages and reminders already posted before you upgrade keep their old buttons until they're redrawn. They still work: the call's old buttons post your card, and an old reminder's buttons reply with a line of text.

Otherwise it waits until no response has changed for 10 minutes, so you can add guests, an eat window, or an offer after tapping **In**; with two or more eating, someone must also be able to cook, pick up, or order. ### Added

- Prebuilt container images on GitHub Container Registry at `ghcr.io/dsmorgan/dinnerbell`. Each release publishes `X.Y.Z`, `X.Y`, and `latest`, and every push to `main` publishes `main` and the short commit SHA. Images carry build provenance and SBOM attestations; [docs/setup.md](docs/setup.md#verify-an-image) shows how to verify one.
- The footer and `/healthz` show the running version, such as `0.2.0`, or `0.2.0+abc1234` for a build from `main`.
- Test instance support ([ADR 0006](docs/adr/0006-test-instance.md)): run a second copy with its own database, Slack app, and hostname.
  - `DINNERBELL_INSTANCE_LABEL` shows a marker such as `TEST` on the web, in Slack posts, on App Home, and in `/healthz`. While it's set, Dinnerbell mentions and messages only members of the configured channel.
  - `DINNERBELL_SLACK_COMMAND` names the slash command. Default: `/dinnerbell`.
  - `DINNERBELL_FEATURES` turns on feature flags. Unknown names stop startup.
  - `dinnerbell scrub-test --keep EMAIL [--keep EMAIL ...] [--yes]` makes a restored production backup safe to use in test. It shows what it will change and asks you to confirm.
  - `deploy/dinnerbell-test` runs every test command with the test project, volume, env file, tag, and port, and refuses unsafe combinations. `deploy/slack-app-manifest.test.yaml` and `.env.test.example` set up the rest.
- `compose.yaml` reads `DINNERBELL_TAG`, `DINNERBELL_ENV_FILE`, and `DINNERBELL_PORT`, which only `deploy/dinnerbell-test` sets. Never set them in `.env` or `export` them: an exported `DINNERBELL_ENV_FILE=.env.test` makes production's own compose commands run with test's settings on production's database.

### Changed

- `compose.yaml` pulls the release image instead of building from source. To build from source, add `-f compose.build.yaml`.
- Production's clone follows release tags: to upgrade, check out the new `vX.Y.Z` tag instead of running `git pull` on `main`.

### Upgrade notes

You switch from building the image to pulling it. Follow "Switch a source-built install to the prebuilt image" in [docs/setup.md](docs/setup.md), which also has undo steps. In short:

1. Note the commit you run now, and back up the database.
2. Run `git fetch --tags && git checkout v0.2.0`, then `podman-compose pull`.
3. Recreate the service: `podman-compose down && podman-compose up -d`.

Run these as the same user and from the same directory as your install. Your data volume keeps its name, so the database carries over. If your install predates M2, its migrations run on start.

podman-compose 1.0.6 or later is required.
