# Channel adapters

This is the contract between Dinnerbell's core and a channel adapter such as Slack. The core decides what happens and records it as typed notifications in the outbox; the adapter only renders and delivers them, and turns button taps back into service calls. Spec sections 9, 13.2, and 13.4 are the background.

## How notifications flow

1. A use case in `services` changes a call and, in the same transaction, writes one outbox row per notification (`db/outbox.py`, table `outbox`). A Slack outage never loses a change.
2. The drainer, `services.outbox.drain`, runs every 5 seconds and after every 30-second scheduler tick; within one process the two never drain at once (`JobContext.drain_lock`). It lists rows that are due (past any retry delay and unclaimed), claims each, commits the claim, calls the channel with no transaction open, and records the outcome. Rows waiting to retry aren't listed, so however many there are, they can't crowd out newer events.
3. The channel is wired once in `app_factory.py` as `JobContext.channel`. It is `channels.base.NullChannel` until Slack replaces it. `NullChannel` logs each notification, reports it delivered, and returns made-up message references, so updates and threads run the same path a real channel takes.

## The interface

`Channel` is defined in `domain/notifications.py`, so `services` can use it without importing `channels`, and `channels/base.py` re-exports it. Adapters implement it structurally; there's nothing to subclass.

```python
class Channel(Protocol):
    async def deliver(self, notification: Notification, *, thread: MessageRef | None = None) -> DeliveryResult: ...
    async def update(self, ref: MessageRef, notification: Notification) -> None: ...
```

- `deliver` posts a new message: to the household channel, or as a direct message to `notification.recipient_id` when that isn't `None`. Return `DeliveryResult(MessageRef(channel_id, message_id))` (for Slack, the channel ID and `ts`) for any post that has a `message_key`, because later updates and threads need it. For other posts the ref is optional.
- `thread` is the message to thread the post under. The drainer passes it when the notification has a `thread_key` and that message was delivered; otherwise it's `None` and you post at the top level.
- `update` edits the message at `ref` to show the notification's state.
- Time out every channel call well under the 5-minute claim lease (`LEASE`). Slack calls should give up within about 30 seconds; the Slack adapter's Web API client times out after 15. A call that hangs past the lease can let a newer update overtake it from another process, and inside one process it holds the drain lock, so no other notification goes out until it returns.
- Raise on failure. The drainer records `"<ExceptionType>: <message>"` in `outbox.last_error`, so never put a token in an exception message.
- Raise `domain.notifications.PermanentDeliveryError` when retrying can't help, such as a deleted channel or a member who left the workspace. The row is marked failed at once, after one attempt, and stops holding back the event's later rows. Raise anything else for failures worth retrying, such as timeouts or rate limits. To ask for a longer wait, as Slack's `Retry-After` does, give the exception a numeric `retry_after` attribute in seconds; the Slack adapter's `SlackRateLimited` does.
- Raise `domain.notifications.ChannelUnavailable` (or a subclass) when the whole channel is down, such as a timeout or an outage. The row retries as usual, and the drainer ends its pass at once, so an outage costs one timeout per pass instead of one per row.
- Raise `domain.notifications.HeldDelivery(message, retry_after=seconds)` when the channel isn't ready for this notification yet, such as while its setup is broken. The drainer gives the row back without counting the attempt and tries again after `retry_after` (at least 5 seconds). A held message-creating post still holds back its event's later rows. The Slack adapter holds channel posts while the bot isn't in the channel, and every delivery while Slack refuses the bot token or it belongs to the wrong workspace.
- A channel may decline to deliver a notification on purpose and return `DeliveryResult(None)`; the row closes as delivered and never retries. The Slack adapter does this on a labeled instance (`DINNERBELL_INSTANCE_LABEL`, ADR 0006), where it direct-messages and mentions only members of the configured channel: a direct message to anyone else is dropped and logged with the member ID (`/healthz` counts them as `slack_dms_dropped`), and a mention of anyone else shows as their plain name. While the channel's members are unknown, such as before the first check, direct messages are held (`HeldDelivery`) instead of dropped, and nobody is mentioned.

## Delivery guarantees

- **Order.** Rows are delivered oldest first per event. A post that creates a message (it has a `message_key`: the call, proposals, and decision posts) holds back its event's later rows while it waits to retry or is claimed by another drainer, so an update or threaded reply never arrives before its message. Nothing else holds rows back: a direct message or a failed update retries on its own schedule. Different events don't block each other.
- **Updates to one message never go backward.** A newer update waits while an older update to the same message is in a channel's hands. An older update that hasn't gone out by the time a newer one exists is closed with `last_error = "superseded by a newer update"` and never sent, even on retry. So the last edit `update` receives for a message always carries the latest state, as long as channel calls finish within `LEASE`. If the newest update then fails for good, the message keeps its last delivered state until the next change, because any older state would have hit the same failure.
- **Once.** A row is claimed with a conditional `UPDATE` before the channel is called, so concurrent drainers never deliver the same row. The claim lasts 5 minutes (`LEASE`). If the process dies mid-delivery, another drainer can redeliver after that, so treat `idempotency_key` as a dedupe key if a duplicate post would matter.
- **Retries.** A failure is retried after 30 seconds, doubling up to an hour. A `HeldDelivery` isn't a failure: it never counts toward `MAX_ATTEMPTS`. When the exception has a numeric `retry_after` (seconds), the next attempt waits for the longer of that and the backoff, at most an hour. After 8 attempts (`MAX_ATTEMPTS`), or at once for `PermanentDeliveryError`, the row is marked `failed_at` and stops holding back later rows. `/healthz` reports `outbox.backlog` (waiting) and `outbox.failed`.
- **Updates without a message.** If the post an update edits never landed (it failed for good, or the channel returned no ref), the update is closed out with `last_error = "no message to update"` instead of being sent.
- **Replies without a thread.** A reply whose class sets `needs_thread` (only `event_cancelled`) means nothing without the call message. If that message never landed, the row is closed with `last_error = "no message to thread under"` instead of being posted at the top level. Other threaded posts still go to the top level.
- **Messages `NullChannel` pretended to post.** `NullChannel` returns refs whose channel ID is `NULL_CHANNEL_ID` (`"null"`, in `domain/notifications.py`). The outbox never passes such a ref to a channel, as `ref` or `thread`. So for a call that opened before Slack was configured, Slack gets no edits for the old call message (they close out as above), and its later posts go to the top level instead of a thread. Never return `"null"` as a real channel ID.

## Keys

Every key of an event's notification starts with the event and its run: `event:{event_id}:run{run}`. An admin re-run increments `run`, so a re-run posts a fresh call message and its own thread. A `schedule_changed` key is `schedule:{slot}:{change_id}` instead.

| Key | Meaning |
|---|---|
| `idempotency_key` | Unique per household. Writing the same key again is ignored, so every transition can be retried safely. |
| `message_key` | Names a message that later notifications edit. Posts with one create it; updates (`is_update`) edit it. Dinnerbell stores the ref the post returned (`outbox.ref_channel`, `outbox.ref_message`), so the adapter needs no table for message refs. |
| `thread_key` | The `message_key` of the message to thread under. |

Updates coalesce: while the newest update to a message is waiting and nobody has tried it yet, a newer update to the same message replaces its payload instead of queueing behind it. Once the newest update has been tried, a newer one gets its own row. Only the newest row ever takes on new state, so an older row given back untried (a `HeldDelivery`) can't absorb the latest state and then be superseded by a row with older state. Ten quick votes become one edit with the latest counts. Each update row's `idempotency_key` is the class key plus a sequence number, such as `event:7:run1:call_updated:3`.

## Notifications

All types are frozen dataclasses in `domain/notifications.py`. Every type but `schedule_changed` has an `event: EventInfo`; for any notification, use `household_id` and `event_id` (None for `schedule_changed`) rather than reaching into `event`. The outbox stores a notification without an event with no `event_id`, so it holds back nothing and nothing holds it back. They carry only domain data: IDs, display names, the event's state and `end_reason`, UTC times plus the household's `timezone`, items with URLs, and the event page's `path` (join it to `DINNERBELL_BASE_URL` for links, per FR-37). A call-off closes the event's undelivered `assignment_made` and `response_reminder` rows unsent, with `last_error = "superseded by a call-off"`. A row a drainer already holds is left to that drainer; if its delivery fails or is held, the drainer checks the call again before the next attempt, and closes the row the same way once the call is cancelled or has started a newer run. Only a delivery already in the channel's hands at the moment of the call-off can still arrive, before the call-off's own messages. A called-off call has `EventInfo.state = cancelled`, with `EventInfo.ended_by` (who called it off) and `EventInfo.end_note` (the reason, if any). Its `call_updated`, `proposals_updated`, and `decision_updated` go out as usual, so the call message can say "Called off by Sam" and the decision can be struck through. A call that was never posted sends only `started_call_cancelled`, and only when someone other than its starter called it off.

Discarding a call (test instance only) deletes the event's outbox rows, pending, held, or sent, except the delivered posts that created a channel message, which stay with `event_id` set to `NULL` as the record of where each message is, so the `call_discarded` updates can find them. A row a drainer holds at that moment is deleted too, so its delivery finds no row to record. Because that delivery may still land, such as an edit of the call message, the `call_discarded` updates then wait out the claim (`available_at` is the discard plus the 5-minute lease), so they arrive last. A post that was in flight when the call was discarded isn't edited: no ref was recorded for it.

A call that got too late to finish after an outage ends with `EventInfo.state = abandoned` and `EventInfo.end_reason = missed`, quietly: Dinnerbell sends no `call_abandoned` post and no direct messages, only `call_updated` (and `proposals_updated` if it was voting) so its existing messages show that it ended. A scheduled call that expires this way was never posted and sends nothing. Render `missed` as a quiet "too late to decide" state, not as a new announcement.

Building blocks: `PersonInfo(id, name)`, `RosterEntry` (status, guests, guests' dietary needs, eat window, offered roles, suggestions, note), `ProposalInfo` (rank, `ItemInfo`, mode, reasons, source, proposer, voters; votes are visible, per FR-14), `DecisionInfo` (proposal, meal time, head count, participants with guests, assignments, guests' dietary notes), and `AssignmentInfo(role, member)`.

Notifications never say who vetoed what. Proposal reasons come from combined preferences only. Nor do they carry anyone's feedback: a done decision looks the same however people rated it.

A guest (#38) is a member row with the role `guest`. `Interactions` lets a guest tap only what `GUEST_TAPS` names (answering In or Out, the roles, and coordinating's logistics) and refuses the rest with `GUESTS_DONT` before any service runs; the services check `domain.guests` again, with whether the guest is invited to that call. A guest's Home lists only the calls they're invited to (`home_view(..., guest=True)`). An unregistered guest's `assignment_made` and `assignment_cancelled` carry `via`, the member who invited them, who is the recipient.

An offer is an event too (`EventInfo.kind` is `offer`), so a call-off, a mark done, feedback, and a discard on a test instance go through the same use cases as a call's. The call actions it has no use for (answering, roles, coordinating, windows, votes, proposals, a re-run, a restart, changing the decision) refuse it with a message to show.

Members are identified by ID. Resolve IDs to Slack users from `member.slack_user_id`. `services.slack_members` has the lookups the adapter needs, because `channels` may not import `db`: the member behind a Slack user ID (`member_for_slack_user`), member IDs to Slack user IDs (`slack_directory`), and linking members found by email.

## Interactions

Map every button or modal to one service call. Services check every rule and permission, scope every ID to the actor's household, write the outbox and audit rows, and commit. The adapter never writes to the database or the outbox itself.

1. Resolve the Slack user to an active member of the household, or refuse with an ephemeral message (spec 13.5).
2. Open a session from the app's `sessionmaker` and call the service with `now=clock()`.
3. Show these exceptions as ephemeral messages with `str(exc)`: `EventRuleViolation`, `InvalidResponse`, `services.errors.NotFound`, and `services.errors.Forbidden`. Show `IllegalTransition` as `str(domain.events.friendly(exc))`: "This call already finished." when the call ended before the action reached it. `calls.cancel_call` and `calls.close_window` already raise that as an `EventRuleViolation`. Anything else is a bug: log it.
4. Don't update shared messages from the interaction handler. The service's notifications do that through the outbox within seconds. The handler updates only messages one person sees, which no notification tracks: their Your answer card and their reminder (below).

Channel messages are shared, so a button can't show whether the person tapping it already voted or offered. Use the toggles: each reads the member's current state under the event's lock and flips it. The explicit `calls.vote`, `calls.unvote`, and `calls.offer_role(..., offered)` remain for surfaces that show the member's own state, such as the web page, App Home, and the Your answer card, where an explicit set survives a double tap.

| Make member, Remove (on `guest_joined`) | `guests.promote(db, admin, guest_id, Role.MEMBER, email=, now=)` with the email Slack shares, and `guests.remove(db, admin, guest_id, now=)` |
| How was it? (on the done decision, the feedback reminder, or Home) | `feedback.form_for_event(db, actor, event_id, run=, now=)` to draw the modal, prefilled with the member's answers |
| Feedback modal | `feedback.give_for_event(db, actor, event_id, FeedbackInput(food=, place=, place_issues=, cook_thanks=, cook_note=), run=, now=)`; empty feedback takes the member's back and returns None |

For what to show a member (their response, which buttons apply to them), use `services.event_views.event_view(db, actor, event_id, now=)`. Its `can` flags come from the same rules the services enforce: `can.cancel` for Call it off, and `can.close_window`, the window Close now would close (`Window.RESPOND` reads "Start the vote now", `Window.VOTE` reads "Decide now"), or `None`, including once that window's deadline has passed.

The Slack adapter shows Close now on a message everyone shares, and Slack confirms it some time after the label was drawn. So the confirmation carries the window it named (`ids.ViewOrigin.window`, or the Home button's `respond:<id>:<run>` or `vote:<id>:<run>`), and the adapter passes it as `calls.close_window(..., expected_window=)`. Under the event's lock, the service raises `WindowMoved` ("The call has moved on since then, so nothing changed.") when the open window is a different one or its deadline has passed, so a late confirmation, or a second one racing the first, closes nothing. Every Slack value and modal for Call it off and Close now also carries the run it was drawn for (`cancel:<id>:<run>`, `close:<id>:<run>`, `ViewOrigin.run`), passed as `run=`, so one left over from before a re-run or a restart gets `StaleRun`. `/dinnerbell cancel` names the call as it is now and passes no run. The ⋯ menu's Close now checks the window's deadline too (`check_expected_window`) before it opens the confirmation, so a pick after the deadline is refused at once.

### Feedback

Once a call is done, its decision message carries **How was it?** (`ids.FEEDBACK`, value `<id>:<run>` from `ids.card_value`), and so do the feedback reminder and each meal in App Home's "How was it?" list (`feedback.awaiting`). Every one goes through `_action`'s identity and place checks and opens the feedback modal (`ids.FEEDBACK_VIEW`), whose `ViewOrigin` names the run; `_submission` refuses a feedback modal without one, and the service checks it again. The modal asks only what the meal takes: the food always, the place and its issue chips for a restaurant, and the cook's thank-you and note for a home meal someone else cooked. The service refuses anyone who didn't eat the meal, and any change after the 7-day window, with an `InvalidFeedback` message to show.

Show a member only their own food and place answers. How many loved each catalog item's food and place (`feedback.item_counts`) and the thank-yous on a meal (`feedback.for_meals`) are all anyone else may see; never show "fine", "not again", or issue chips, not even as counts, and only the cook a thank-you named gets its sender and note. Never log a rating.

### Your answer cards and the reminder

While responses are open, the call message's only choice is **Answer** (`ids.ANSWER`, value `<id>:<run>` from `ids.card_value`). It goes through `_action`'s checks and the card lock, changes nothing, and posts the tapper's Your answer card (`messages.your_answer`); for an earlier run, or once responses have closed, the card says the call moved on. Call messages posted before **Answer** existed still have **In**, **Maybe**, **Out**, the role offers, **I'll coordinate**, and **Details**, without a run, until they're redrawn; those handlers stay, and also answer with a card. While voting with no coordinator, **I'll coordinate** stays on the call message, since no card is offered then. It's `ids.CALL_COORDINATE`, with `<id>:<run>`, and works only on the call message, like **Answer**, so a voting message from before a restart can't claim the newer run; the older `ids.COORDINATE`, without a run, stays for messages drawn before it. The card is an ephemeral in the channel, drawn from `event_views.event_view`, with the member's own answer and offers selected (primary, and "✓ " before the text). The card's buttons (`ids.CARD_ACTIONS`) carry `<id>:<run>` (`ids.card_value`) and go through the same identity and place checks as every button. They pass the run to the service (`calls.respond`, `calls.offer_role`, `calls.claim_coordinator`, and `calls.save_details` from the card's Details modal all take `run=`), which checks it under the event's lock and raises `StaleRun` for a card drawn before a restart or re-run.

A Slack ephemeral can't be edited with `chat.update`. Only the `response_url` that comes with a tap on the ephemeral itself can replace it, for 30 minutes and 5 uses. So:

- **Answer**, or an old button, on the call message posts a new card with `chat.postEphemeral`. Its own `response_url` belongs to the call message; `replace_original` there would rewrite the call for everyone, so the adapter never uses it.
- A tap on a card (`container.is_ephemeral` true, in the household channel) replaces that card through the tap's `response_url` with `replace_original`. The adapter accepts only a URL whose whole string matches `https://hooks.slack(-gov)?.com/actions/<team>/<number>/<token>` (`ids.response_url`), so the string it checks is the string it sends. It never logs the URL, and posts a new card if Slack refuses.
- A card button anywhere else, such as on the call message or Home, isn't one the app drew, and gets "That button is out of date."

The card shows what the member chose, and why a tap changed nothing, such as someone else coordinating. Claiming coordinating again as the coordinator changes nothing and isn't an error, so a double tap or a retried delivery doesn't complain. One person's taps on one call run one at a time (an in-process lock per Slack user and event, from reading the response through replacing or posting the card, dropped when nobody holds it), so two quick taps can't land out of order. Once the call has started again, closed responses, or been called off, it says "This call moved on." with the call's state and no answer buttons.

The reminder uses the same card buttons, so it names its run too. The Details modal names the run it was opened for wherever it's opened (`ViewOrigin.run`), and `calls.save_details(..., run=)` refuses a save after a restart. A tap on the reminder edits the reminder with `chat.update` (the message is the bot's own, in the member's DM, whose `ts` comes with the tap) to show the answer, or that the call moved on. Reminders sent before cards existed still have the call message's buttons and get a line of text back.

## Showing the version

Some replies call no use case, such as help and the `version` subcommand. They need no member, only a request from the right workspace. Nothing they show is secret: `/healthz` shows the version and the instance label, and the schema revision follows from the version.

- The version is `Settings.version_label`, which the web footer and `/healthz` use too: `0.3.0` on a release, `0.3.0+abc1234` on a `main` build. The composition root passes it to the adapter (`SlackConnection(version=)`); don't build it again from `__version__`.
- The schema revision is `services.health.schema_revision()`. It reads the migration scripts from disk, so the composition root calls it once at startup and passes the result (`SlackConnection(schema_revision=)`). `dinnerbell serve` migrates the database to it before it starts, and refuses a database at a revision it doesn't know, so while the app runs it's the database's revision too.
- The Slack adapter's `blocks.version_line` and `blocks.version_link` render both, with the instance label, and `blocks.with_version_footer` adds the line to the bottom of every Home tab it publishes, unless the tab already has Slack's 100 blocks.
